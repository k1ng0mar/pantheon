# Architecture sweep, September 24, 2026

Post-REPL pass over every crate, looking for structural flaws, missing
safeguards, inconsistent patterns, and decisions that bite later. Fixed
what was clear-cut; the rest is flagged with the decision it needs.

## Fixed this pass

1. **Memory laundering via markdown round-trip (critical, fixed).**
   `export` wrote only key/value; `import` re-tagged everything as User
   tier. An untrusted record that traveled through MEMORY.md came back
   trusted. That was a bypass of the anti-laundering invariant exactly
   where a human is in the loop and least likely to notice. Fix: v2
   export format carries a `{trust=...}` footer per record, parse reads
   it back, import preserves it; hand-edited/legacy files still import
   as User (a human typed it). Regression test proves the round-trip.
   Commit a2ca1cf.

2. **`memory confirm` missing from the CLI (fixed).** The promotion tool
   existed for the model but no CLI verb, and the docs referenced one
   that did not exist. Added `pantheon memory confirm KEY`; a confirm on
   a user-tier record is now a clear no-op instead of a missing-row
   error. Commit bcccfde.

3. **Eval coverage for the danger gate (fixed).** The pre-gate had unit
   tests but no end-to-end case driving the real binary. Added
   `danger-gate-blocks-shell-wipe`: mock-driven shell call with
   `rm -rf /` must fail the run with DANGER_BLOCKED. Commit a288554.

4. **Docs drift for the new surfaces (fixed).** README, getting-started,
   cli.md, memory.md now describe the REPL, the confirm verb, trust
   tiers, and the pre-gate. Commit 5b922a8.

## Flagged: needs a decision

### 1. The serve surface has no authentication (high)

`pantheon serve` binds 127.0.0.1 by default (good), but `/agui/rpc`
accepts unauthenticated `agui.send`, `agui.grant`, `agui.deny`. Any
local process can drive runs and approve tool calls. The web UI it
serves is likewise unauthenticated. Today this is a single-user dev
tool, so the risk is local-only. The moment this binds 0.0.0.0 or sits
behind a tunnel (the Cloudflare setup on this box does exactly that),
it is remote code execution as a service.

Decision needed: bearer token in config (checked on every RPC), or
accept "localhost only" and document it loudly. Recommendation: token,
generated by `setup`, checked in `handle_one`. Small change, do it
before any non-local bind.

### 2. The gateway is an unauthenticated remote shell (high)

`pantheon gateway` runs Telegram/Discord messages straight into
`session.chat` with `coder_with_memory`. Anyone who can message the bot
can run shell commands on the host under the coder policy. The danger
pre-gate now limits the worst cases, and approval gating holds for
capabilities in the approval list, but shell itself is granted outright
to coder.

Decision needed: per-surface allowlist of chat ids (Telegram user id,
Discord user id) that maps to a policy; unknown senders get read-only
or nothing. Recommendation: `PANTHEON_GATEWAY_ALLOW` env with comma-
separated ids, enforced in `route_event`, plus a stricter default
policy for gateway sessions than the CLI uses. This is the single most
exposed surface in the project.

### 3. Orphan crates: seven spec sections with zero consumers (medium)

otel, migrate, swarm, mcp, scheduler, secrets, sandbox: each compiles
and passes its own tests, none is referenced outside itself. They are
not dead code in the "delete it" sense; they are built-ahead
capabilities with no wiring. The risk is drift: their APIs were written
before the crates they would serve existed, so the first integration
attempt will likely require reshaping them.

Decision needed: pick the next one to wire (secrets is the natural
next, per the roadmap) and accept that the others stay unwired, or
delete the ones with no near-term plan to reduce maintenance surface.
Recommendation: keep sandbox + secrets (they back the roadmap), delete
mcp (the adapter-not-host decision makes it redundant) and swarm unless
multi-agent work starts within a month.

### 4. The sandbox crate is a mapping, not a sandbox (medium)

`SandboxLevel::for_capability` maps capabilities to levels and
`enforce` maps policy decisions onto level names, but nothing enforces
anything: the shell tool spawns `sh -c` with no rlimits, no cwd
pinning, no network restriction. The crate is honest about this
("policy mapping only" in the docs) but the name oversells it.

Decision needed: when to land Phase A (bubblewrap/namespace backend
behind `enforce`). Until then the docs should keep saying plainly that
Medium/High/VeryHigh are labels. The dangerous-pattern gate narrows the
top of the risk, not the breadth.

### 5. Shell tool inherits the daemon's cwd (low, but document it)

`sh -c` runs wherever `pantheon` was started. A REPL started in `~/`
lets the model read anything readable there. Combined with
FilesystemRead being granted by every preset, the effective read scope
is "everything the user can read." That is a legitimate choice for a
local tool, but it should be a documented, explicit choice, and the
REPL could pin cwd to the project dir. Decision: document as-is, or pin
`cwd` to a configured workspace root. Recommendation: document now, pin
when sandbox Phase A lands (the same mechanism sets cwd).

### 6. Budget defaults are turn-based, not token-based (low)

`Budget { max_turns: 16, max_tool_calls: 32 }` bounds loop length but
not token spend. A 16-turn conversation with a large-context model can
cost real money with no ceiling. Compaction (roadmap item 5) partially
addresses context growth; a token budget is a separate control.

Decision needed: add `max_total_tokens` to Budget now or with the
compaction work. Recommendation: with compaction, since usage numbers
are already collected per turn in the model events.

### 7. `run` verb bypasses the terminal-run check (low, deliberate?)

`pantheon run --id X` on a completed run appends new events under the
old run without reopening it (start_run does not check status). The
rerun eval depends on this ("re-running a completed run appends events
without breaking history"), but it means two writers can disagree about
what a "run" is: chat treats terminal as a wall, run treats it as
suggestion. Recommendation: keep (it is the eval/test harness path and
the ledger stays honest), but the docs for `run` should say it is not
subject to the session lifecycle.

### 8. Hook surface is still pre-LLM only (known roadmap)

PreToolUse/PostToolUse/RunStart/RunStop remain unbuilt (roadmap item
4). The dangerous-pattern gate now sits in the shell tool itself, which
is the right layer for it; when tool hooks land, the gate stays in
front of them by construction.

## Clean bills (checked, no action)

- Ledger append is transactional with terminal-status guards; reopen is
  scoped to terminal statuses only.
- Approval grant/deny flows keep `has_pending_approval` semantics
  intact with the new reopen path.
- Lease acquisition/heartbeat unchanged by the REPL (one session per
  process, RunLeaseGuard as before).
- Plugin tools and executable plugin scripts still pass the capability
  gate; nothing in the new code bypasses it.
- The REPL's slash commands never reach the model (handled before
  `session.chat`).
- Markdown sync conflict detection unaffected by the v2 footer (the
  footer is part of the hashed render, so any tier change invalidates
  the store hash, which is correct).
