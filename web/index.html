Where the authority sits

Agent products lose trust when a successful prompt turns into an accidental file write, an exposed credential, or an unrecoverable process. Pantheon treats those as runtime behaviour rather than prompt instructions: a model may request, the runtime decides, and both halves get written down.

The model — swappable

  • Produces text and reasoning
  • Requests a tool call
  • Proposes a memory record
  • Never selects its own replacement, its own permissions, or its own budget

Dashed rule: this side is expected to change.

The runtime — load-bearing

  • Run state, leases, and cancellation intent
  • Capability and policy decisions, before the tool runs
  • Execution in process groups tied to the run lease
  • The append-only ledger, and replay of it
  • Recovery after the process stops
  • Memory access with provenance and trust tiers
  • Delivery to every surface

Solid rule: this side is what you depend on.

Three presets, defined in code

Pick one with policy = "coder" in config.toml. They are code-defined, not free-form config — deliberately, because free-form capability config is how agents end up with more access than anyone intended. To change what a preset allows, you change pantheon-core/src/capability.rs and ship it.

PresetFilesystemShellGitMemory writeWhy you'd pick it
reader read no read no Nothing executes. Safe for untrusted tasks.
coder (default) read/write execute read/write, push needs approval no The working default.
coder_memory read/write execute read/write, push needs approval yes Same as coder, and the agent can persist memory.

Secrets stay out of context

The config file names an environment variable and never holds a value: api_key_env = "OPENAI_API_KEY". The runtime resolves it at session start. A model that asks for a secret gets the effect of the secret, not its bytes in the transcript or the ledger.

The gate runs before the tool

Tools declare the capability they need. The agent loop enforces the policy decision before execution, and shell commands additionally hit a dangerous-pattern pre-gate. A model cannot grant itself anything, because it is not on the side of the boundary that grants.

The record, and four ways to read it

Runs are stored as an append-only sequence of typed events. Terminal statuses are guarded in the append path, so a finished run cannot quietly change its mind. Debugging, handoff, compliance review, and tests all read the same rows. 

$ pantheon explain run_1790413737088_9031
run run_1790413737088_9031: 4 events
  #62 started
  #63 tool started: bash
  #64 progress: list the files in this directory
  #65 completed

Output from the installed binary, not a rendering of one.

VerbQuestion it answers
explain <run_id> What happened, in order, including why each decision was made.
status <run_id> Where this run is now — running, completed, failed.
audit <run_id> [OUT] A sequence-checked JSONL trajectory you can diff or hand to a reviewer.
stream <run_id> --after N SSE frames from sequence N, so a dropped client resumes instead of replaying blind.

When it needs you, it stops and asks

A gated tool call parks the turn instead of dropping it. The runtime writes ApprovalRequested and waits. Your answer is ApprovalGranted or ApprovalDenied — durable operations in the same ledger, so the decision outlives the process that asked. 

pantheon grant <run_id> <scope>   # approve a parked tool call
pantheon deny  <run_id> [scope]   # refuse it

Verb shapes lifted from pantheon --help. Scopes are capability-bound, so approving git.push does not widen anything else.

Four delivery mechanisms, one approval model. The channel never becomes the source of truth — the ledger does.

Crash recovery is a query

A real failed run on this machine, as the CLI reports it:

$ pantheon status run_1790414395478_1399
failed

$ pantheon explain run_1790414395478_1399
run run_1790414395478_1399: 2 events
  #66 started
  #67 FAILED (5)

Because the failure is a row, "did it survive?" has an answer. A killed process leaves a lease behind; the next start reads the ledger, emits RunRecovered, and continues from committed state.

  • run_leases — a live run holds a lease, so two processes cannot drive one run.
  • operations — tool work advances through translation, execution, result translation; the operation id is the idempotency key, so a retry does not fire twice.
  • run_process_groups — child processes are tied to the lease, so cancellation reaches the shell the agent spawned, not only the agent.
  • cancel — intent is persisted before the process is terminated, so a crash mid-cancel is still a recorded decision.
  • watchdog — probes activity and ledger health after a stall instead of waiting forever.

Memory has a trust tier, not just a score

Pantheon does not let the model promote its own guess to durable knowledge. A write needs MemoryWrite, which only coder_memory grants, and every record keeps its provenance through retrieval: 

pantheon_memory/src/write.rs
  → write_with_mode()
    → memory_write_policy_allows(action, mode)   // denies unless MemoryWrite
    → SQLiteMemoryStore.save(record)

pantheon_memory/src/recall.rs
  → memory_recall()
    → HybridRetriever.search()   // BM25 + vector + graph
    → trust tier re-ranking
  • Retrieval is hybrid: BM25 + vector + graph, with a cross-encoder reranker and multi-query expansion.
  • Scores are normalised and bounded before anything is ranked.
  • Confidence and trust tier feed reinforcement, retrieval, and decay — so unverified agent-written records stop crowding out verified ones.
  • claims in the ledger carry evidence state; entities / relations / timeline carry the graph.
  • consolidation is a CLI subcommand whose tests run under MIRMURA_ONLY=1 in CI, so they never need a live model.

One runtime, several front doors

Every surface talks to the same engine over an in-process JSON-RPC bus, so the orchestrator, the ledger, and the UI share one source of truth without a socket hop.

terminal

pantheon run / tui / chat

Ratatui session with live tool traces, cost and token counts, permission cards inline.

local web

pantheon serve

Local AG-UI surface: JSON-RPC plus SSE event streams over plain std HTTP.

Discord

channel_allowlist

Slash commands, button-based approval, 1500-char chunking.

Telegram

chat_allowlist

Long-polling with an allowlist that defaults closed: no chat ids, no replies.
