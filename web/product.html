PRODUCT TOUR

Authority lives in the runtime.
Everything else is replaceable.

Agent products lose trust when a good prompt turns into an accidental file write, an exposed credential, or a process that can't be resumed. Pantheon treats those as runtime behavior: a model may request, the runtime decides, and both halves get written down.

Where the authority sits

The model — swappable

  • Produces text and reasoning
  • Requests tool calls
  • Proposes memory records
  • Never selects its replacement, its permissions, or its budget

Dashed rule: this side is expected to change.

The runtime — load-bearing

  • Run state, leases, and cancellation
  • Capability and policy decisions, before tools run
  • Execution in lease-owned process groups
  • The append-only ledger, and replay of it
  • Recovery after the process stops
  • Memory access with provenance and trust tiers

Solid rule: this side is what you depend on.

Presets are code-defined with policy = "coder" in config.toml — deliberately, because free-form capability config is how agents end up with more access than anyone intended. Secrets work the same way: config names an env var (api_key_env = "OPENAI_API_KEY"), the runtime resolves it at the execution boundary, and values never enter context, logs, or the ledger.

The record, and three ways to read it

Runs are an append-only sequence of typed events in SQLite. Terminal states are guarded in the append path — a finished run can't quietly change its mind. Debugging, handoff, and review all read the same rows.

CommandQuestion it answers
pantheon runs <id>What happened, in order — including every approval decision.
pantheon runsWhere every run stands: running, awaiting_approval, completed, failed, canceled.
pantheon audit <id> [OUT]A sequence-checked JSONL trajectory for scripts and reviewers.
pantheon logs [errors] [-f]What the process has been doing — including failures before any run existed.

When it needs you, it stops and asks

A gated call parks the turn instead of dropping it. The decision is a durable ledger entry, so it outlives the process that asked — answer inline, or from anywhere:

pantheon run --taskID <id> --grant <scope>   # approve, then continue
pantheon run --taskID <id> --deny <scope>     # refuse; recorded, run continues

Scopes are capability-bound: approving git.push widens nothing else. A scope resolves exactly once.

SurfaceHow you answer
terminalPermission card inline (y / n)
local webGrant / Deny buttons on the session
DiscordButtons carrying the scope in their action id
TelegramInline keyboard; the tap resolves the scope

Four mechanisms, one approval model. The channel never becomes the source of truth — the ledger does.

A failed process is not a lost task

$ pantheon runs run_1790414395478_1399
run run_1790414395478_1399: 2 events
  #66 started
  #67 FAILED (5)

Because the failure is a row, "did it survive?" has an answer. Resume with the same run id: finished calls are skipped from recorded results, interrupted ones re-execute. pantheon repair settles anything stranded, backing up first.

  • Leases — one supervisor owns a run; a second can't double-execute it.
  • Durable operations — tool work advances through persisted phases; the operation id is the idempotency key.
  • Process groups — children are tied to the lease, so cancel reaches the shell the agent spawned.
  • Budgets — runtime-owned caps on turns and tool calls; overshoot is rejected before it executes.

Memory with trust, not just scores

Five layers — global, agent, project, task, ephemeral — behind one gated write path: propose → policy → provenance → validation → store. Retrieval blends full-text search with embedding similarity, then ranks with trust awareness:

TierMeaning
systemHarness-authored, authoritative.
userYou wrote it — CLI, /remember, edited MEMORY.md.
memoryConfirmed by you (memory confirm).
untrustedModel-proposed or tool-derived. Never promotes itself.

A document saying "ignore your instructions" is data, not an order. Recurring discoveries graduate into versioned pantheon skills — knowledge that explains how, never authority that permits. Full story: Memory.

One runtime, several front doors

Every surface drives the same Session runtime off the same ledger. Switching screens mid-conversation loses nothing.

terminal

pantheon

Interactive session with history, inline approvals, mid-conversation model switches.

scripts

pantheon run

One-shot turns for CI and automation, delivered locally or to a channel.

local web

pantheon serve

AG-UI client replaying the ledger stream. Minimal reference surface.

messaging

pantheon gateway

Discord and Telegram behind a required pairing allowlist; replies chunked to platform limits.
